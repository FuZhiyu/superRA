# Task-scoped reproduction

The declared graph records complete provenance. Each invocation selects an execution scope; saved artifacts supply inputs from outside it. The default runs only selected work. Upstream expansion and forced execution are independent choices.

## Decision status

The researcher selected task/step targets, task-scoped execution without a scope keyword, upstream execution on demand, and default registration of executable support for retained results. Task targets include their own steps and all active nested tasks; multiple targets select their union. This design proposes `--upstream` for expansion and `--force` for execution of fresh steps within the resulting scope.

Canonical selectors are bare task paths and `task#step`. During migration, existing bare step names remain accepted only when unambiguous.

Task-scoped execution uses existing upstream inputs without an override or successful-build baseline. It records unverified provenance when appropriate. These scope, selector, and saved-input choices are settled.

## Selection determines the execution boundary

| Selector | Selected steps |
| --- | --- |
| `analysis` | Steps owned by that task and its active descendants |
| `'analysis#estimate'` | That one step, verified to belong to that task |
| Multiple task/step selectors | Union, deduplicated |
| No targets | Steps at `required` tier |
| `--tier on-demand` or `--tier all` without targets | Steps at that tier, or every active registered step |

Task paths are relative to the task root, independent of the shell's current subdirectory. `.` selects all active task-owned steps, including umbrella-root steps; `.#step` selects an umbrella-root step. Quote selectors containing `#` in examples. Keep existing global step-name uniqueness; qualified targeting does not change step identity or lock keys.

Explicit targets and an explicitly supplied `--tier` are mutually exclusive. An invalid target rejects the invocation before any execution; an explicit task with no steps reports that it selects no work. Empty selections certify no result and completion gates reject them when results need coverage. Overlapping task and step selectors never duplicate execution.

A step target selects only that step, including when its producer belongs to the same task. Name the containing task to include its other steps. Internal edges order selected steps; every consumed artifact whose producer is outside the selection crosses the run boundary. Multiple selections need not form a continuous dependency chain: selecting A and C from A → B → C uses saved B output and reports B as outside scope.

Logical task prerequisites still govern task-development readiness. They do not select scripts. Global declaration and cycle validation remains mandatory; an upstream execution failure or stale result is distinct from an invalid graph.

## Two flags compose

| Command | Effective execution scope and behavior |
| --- | --- |
| `repro build analysis report` | Selected tasks, incremental |
| `repro build 'analysis#estimate'` | One step, incremental |
| `repro build report --upstream` | Selection plus transitive file-producer ancestors, incremental |
| `repro build report --force` | Force every selected step; no scope expansion |
| `repro build report --upstream --force` | Force the entire selected producer chain |
| `repro build --tier all --force` | Force every active registered step |

Expansion crosses tiers but adds only actual producer ancestors, never all steps in an upstream owner's task. Downstream consumers outside the selection are never implicitly executed. Missing boundary inputs never trigger automatic expansion. `--force` applies after expansion and bypasses reviewed acceptance for every step in that effective scope.

`build`, `status`, and `build --dry-run` resolve the same targets and `--upstream` boundary. Force is build-only. Dry-run reports selected steps, added ancestors, boundary files, and expected execution without changing outputs or evidence; downstream execution after an incremental upstream rebuild remains conditional on regenerated bytes.

## Saved-input reuse does not certify the producer

Use existing artifacts from out-of-scope producers by default, including when their producer is stale or failed, their bytes differ from the last successful output, or no successful-build record exists. Available successful output evidence informs provenance reporting, not permission to execute. Producer state remains unchanged. Unproduced external inputs retain the existing declared-boundary behavior.

Missing inputs block the scoped run and name their producer; existing inputs require no `--use-existing` flag or approval gate. Preview and execution reports identify the boundary files and whether they match successful output evidence, differ from it, or lack it. The consumer receipt records the bytes actually used and their provenance. Reuse never certifies the producer, clears its failure, or serves as reviewed acceptance. Changed boundary bytes invalidate selected consumers and are used by their next scoped rebuild without an extra override. Content validity remains the responsibility of the selected producers and checks; even a partially written upstream artifact may be attempted, with failures reported by those steps.

Hash the actual consumed artifacts when establishing the boundary. A sidecar alone cannot prove that a failed producer left its output intact. Reuse trustworthy recorded full digests where available; preserve efficient warm hashing. Record producer identity, logical/resolved input paths, content fingerprints, and baseline/provenance classification with execution evidence. Detect boundary changes during execution and withhold a successful receipt. No mandatory copy of large datasets is introduced.

## Scoped freshness and upstream freshness are separate facts

Assess execution freshness against the selected graph and the recorded boundary. Report upstream provenance separately, for example: “report fresh for saved inputs; analysis stale upstream.” Default scoped status succeeds when selected work and its boundary evidence are current, even if out-of-scope producers are stale or failed. `status --upstream` assesses the expanded chain and fails on unresolved upstream work.

Successful local execution updates only steps actually run. Preserve existing successful locks, retries after failed forced execution, acceptance evidence, and real last-run metadata. Add scope and boundary information without changing persisted workflow task statuses. Existing global freshness remains available to the task reader and dashboard; scoped success must not turn an upstream-stale pipeline globally green.

Changing a boundary artifact invalidates its selected consumers. Editing an out-of-scope producer without changing its saved output does not invalidate local execution evidence. If that producer later succeeds with identical bytes, full-chain status can become fresh without rerunning downstream steps. Existing reviewed acceptance retains its stronger evidence requirements; saved-input reuse cannot manufacture acceptance.

## Concurrent task work does not invalidate unrelated execution

Freeze the selected step set for an invocation. Check the selected execution contract before execution and before recording success: step commands/specifications, resolved input/output paths, and producer ownership relevant to consumed or written artifacts. Adding unrelated tasks, changing workflow statuses or prose, or editing unused config entries must not abort running work. New steps outside the frozen selection wait for the next invocation.

Retain full graph validation at invocation start. During a build, changes that alter the frozen contract or create conflicting ownership of its artifacts reject affected execution evidence with a specific reason; unrelated graph changes do not retroactively invalidate that run. Guard actual input bytes during execution independently. Keep the acceptance preview/apply transaction's own consistency checks; a narrower build guard cannot authorize stale acceptance.

## Registration and workflow integration

The reproduction skill owns result coverage: executable producers and supporting checks for retained task results are registered by default, or referenced when already registered. The requirement includes unchanged scripts used for new results and task companions, with coverage to an agreed external-input boundary. Preserve exclusions for uncited scratch work and machine-specific artifacts. Registration does not promote steps to `required`.

Broaden the shared `using-superra` Task Interface load trigger beyond already-configured trees and maintained-output edits. Route planning, tree changes, interactive execution, roles, and integration through that owner rather than duplicating the coverage rule. Planning seeds known output ownership; implementation completes executable declarations; tree changes reconcile results, dependencies, and ownership together.

Task-local verification uses default scoped build/status. IMPLEMENT phase exit and integration protection/final verification explicitly use `--tier required --upstream` to preserve their pipeline-coverage guarantee. Force remains an additional researcher-selected verification choice. A selected protection check must be in the target/tier selection; consuming a result alone does not automatically select every downstream check. Keep claims scoped to the recorded input boundary and distinguish execution from reviewed acceptance.

## Migration and implementation ownership

Change the default deliberately in the unreleased reproduction upgrade; do not silently preserve automatic upstream expansion for legacy selectors. Existing bare step names may remain compatibility inputs only when they resolve unambiguously; a task/step collision errors with explicit alternatives. New examples use canonical task and qualified-step targets. Retire `--force-all` with an actionable error pointing to `--upstream --force`, rather than retaining a third forcing mode. Existing locks and declarations remain readable without a bulk rewrite.

## Behavioral verification

Use disposable shell-step fixtures; assert commands actually executed as well as reported state.

| Case | Required evidence |
| --- | --- |
| Task, nested task, umbrella, qualified step, mixed/overlapping targets | Exact selection; no implicit upstream or downstream execution; ambiguous/invalid/empty selection diagnostics |
| B/C selected; A stale or failed; successful saved A output intact | B/C execute as needed; A untouched; local status passes and upstream status exposes A |
| Missing boundary | Block and name the missing input/producer; no automatic scope expansion |
| Changed or unverified boundary; failed A partially overwrites an output | Attempt selected work with existing bytes without an override; record provenance, invalidate affected consumers, and preserve producer failure; selected checks may reject the content |
| Boundary mutation during a run; sidecar-backed input | No false successful receipt or trust based solely on a sidecar |
| Concurrent unrelated task creation/status/config edit versus selected command/path/ownership edit | Unrelated edits preserve the run; relevant changes prevent a false successful receipt and identify the changed contract |
| A/C selected with B omitted | C consumes saved B; diagnostics retain the omitted producer; no accidental B execution |
| Scope, upstream expansion, force, and both together | Exact executed sets across tiers; force never expands scope by itself |
| Fresh repeat, upstream code-only edit, input change, identical upstream regeneration | Correct local/full status distinction and unchanged-output cutoff |
| Accepted result, forced failure, retry, legacy lock | No acceptance laundering or fabricated execution evidence; failed forced work requires retry |
| No-target required selection and required upstream completion | Default remains bounded; explicit completion scope includes true producers and selected checks; empty selection is not verification |
| Dry-run, parallel execution, live reader, dashboard/export | Selection/evidence agreement, no preview writes, honest scope display |
| Registration from an unconfigured tree and interactive result capture | Realistic agent/script-level verification covers planning, edits, result recording, and completion routing |
| Isolated existing project | Upgrade preview, scoped execution without upstream mutation, opt-in upstream run, old-selector/flag diagnostics, boundary evidence and warm latency |

The existing-project pilot may use a bounded fixture derived from the project when full upstream execution is costly; report precisely which scope was executed. No runtime result is claimed by this design document.
