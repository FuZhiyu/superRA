# Reproducibility design review, 2026-09-28

The core freshness rule is sound, but the branch is not ready to ship. A step counts as fresh only when its current bytes match a recorded successful run or an exact reviewed acceptance, so a merged or cloned lock can make a step stale but never falsely fresh. Around that core, five read-only reviewers at `7d5fa992` found one false `fresh`, several breakages in a Dropbox / multi-machine / git-merge setup, an inconsistent readiness model, contradictions in the workflow wiring, and agent instructions that fail CLAUDE.md's gate in both directions.

Findings marked **(direct)** were reproduced or read by the orchestrating reviewer; the rest were reproduced by a review agent on scratch projects unless marked *inferred*. Detailed evidence: [gate-audit.md](gate-audit.md), [wiring.md](wiring.md), [deps-report.md](deps-report.md); the engine and dashboard findings are carried in their subtasks.

## 1. Correctness bugs, most severe first

1. **False `fresh` when data sits behind a symlinked subfolder.** `tree_hash` ([_repro_state.py:180](../../../../skills/task-tree/scripts/_repro_state.py#L180)) calls `os.walk` without following links **(direct, in the code)**. An edited file under a symlinked folder inside a declared data directory left the step fresh; `build` skipped it and the output kept the old value. worktree-data-sync creates exactly these links. → [01](../01-engine-freshness/task.md)
2. **One unset environment variable on one machine freezes the whole tree there (direct).** With `OUT: {env: NOPE_UNSET_VAR}`, both `task frontier` and `task create` refuse to run. → [03](../03-readiness-model/task.md)
3. **Upgrading breaks projects that used tiers (direct).** A leftover `tier:` key is an `[ERROR]` that stops `task frontier`; `--tier` gets a generic argparse error. [RELEASE-NOTES.md:15](../../../../RELEASE-NOTES.md#L15) promises a warning and actionable errors. → [09](../09-upgrade-and-records/task.md)
4. **pytask's own database overrides the lock.** With `pytask.lock` deleted and `.pytask/` kept, `status` says 5 steps are missing while `build` skips all 5. → [01](../01-engine-freshness/task.md)
5. **False cycles once a parent task owns steps.** Two levels up, the parent's own steps collapse into one node; a valid setup → robustness → estimate chain is rejected and the frontier empties. → [03](../03-readiness-model/task.md)
6. **A targeted build reruns the consumer of a large sidecar-tracked file** with nothing changed. → [01](../01-engine-freshness/task.md)

## 2. Committed state does not fit Dropbox, multiple machines, or merges

- **Machine-specific data is committed:** absolute resolved paths and `actor = getpass.getuser()` in `repro-acceptance.json` ([_repro_acceptance.py:414](../../../../skills/task-tree/scripts/_repro_acceptance.py#L414), **direct**); `env_probe` stdout verbatim.
- **Merges conflict:** two branches accepting different steps conflict on `repro-acceptance.json` (~3.5 KB per step), and a conflicted file disables every `repro` command; `repro-builds.json` churns on `built_at`, which nothing reads.
- **"Local" state syncs:** `.superra-repro/` is only gitignored, so Dropbox carries run records across machines (*inferred*).
- → [02](../02-portable-records/task.md)

## 3. The readiness model is inconsistent

- Cross-branch readiness uses status; parent-to-child readiness uses step freshness; stale "own work" appears for approved parents but not approved leaves.
- Adding a subtask rolls an approved producer back and blocks consumers of unchanged files.
- The producer-edit reminder compares content, so Bash heredoc edits are caught, but it misses `${VAR}` paths, files in declared directories, the first call of a session, and new scripts.
- → [03](../03-readiness-model/task.md), [04](../04-edit-hook/task.md)

## 4. Agent instructions fail CLAUDE.md's gate

- **DRY:** ~30% (~2,100 words) of agent-loaded reproduction text is duplication; saved-input / `--upstream` semantics appear 10 times.
- **Too compressed:** "boundary" has two meanings; the stale rule's classes are not exhaustive; "completion targets" is used before definition.
- **Conflicting gate (direct):** `designing-the-graph.md:9` blocks on every drift test; `protect-and-completion.md:8` registers only researcher-selected ones.
- **Load surface:** subagents are routed into `commands.md`, which CLAUDE.md:135 disallows.
- **Wiring (direct):** the completion gate builds before applying the stale rule, so costly steps run without the researcher; the planner's outs-only seeding produces invalid steps.
- → [07](../07-instruction-rewrite/task.md), [08](../08-workflow-wiring/task.md)

## 5. Over-built for the value

- Acceptance: the token apply step, the `upstream` field, evidence hashing, and committed copies of local evidence.
- pytask coupling: four private-API imports and hook-order dependence for ordering and lock writing superRA could own.
- Dashboard: ~100 lines of dead JS, ~40% duplicated payload, 27–58% initial zoom.
- `explain`: drops the relation to HEAD for tracked outputs, ignores graph errors, repeats rows per consumer.
- → [01](../01-engine-freshness/task.md), [02](../02-portable-records/task.md), [05](../05-explain-impact/task.md), [06](../06-dashboard/task.md)
